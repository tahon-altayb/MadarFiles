# فشل دفعة GPU بعد نجاح التهيئة · تقرير المستخدم

التقرير الجديد على CELLULAR / API 37 يثبت الجاهزية عند 31 ثانية، واكتمال رفع الصوت عند 57 ثانية، وبدء العامل bootstrap عند 60 ثانية، ثم MUSIC_PROCESS_EXIT عند 62 ثانية. انقطاع WebSocket سبق نجاح التهيئة أيضًا؛ لا يثبت التقرير أنه سبب خروج العامل. لم تُنتَج دفعة صوت موثقة في هذا التقرير.

وجدت المراجعة سباقًا مثبتًا: قد يكتب العامل حالة failed الأصلية بين قراءة ملف التقدم وفحص poll()، ثم يستبدلها bootstrap برمز عام MUSIC_PROCESS_EXIT. التصحيح يعيد قراءة الحالة بعد رصد الخروج، ويحفظ done/failed، ويميز الخروج بإشارة NATIVE_ABORT عن PROCESS_EXIT مع exit_code. الاختبارات الجديدة تعيد سباق الكتابة وخروج الإشارات -6/-9/-11 وخروج Python برمز 1؛ نجحت اختبارات العامل التسعة محليًا.

هذا التصحيح يحافظ على سبب الفشل ولا يثبت سبب الخروج الأصلي بحساب المستخدم. لم يُبنَ APK جديد بناءً على تخمين. يلزم اختبار استدلال GPU فعلي لتحديد سبب العطل؛ اختبارات Android والمحاكي لا تستبدل ذلك.

الدفتر diagnostics/Madar_GPU_Diagnostic.ipynb يتضمن نص عامل الإصدار 1.9.6 نفسه. ينشئ عملية مستقلة مملوكة للفحص، ويجهز النموذج ثم ينفذ دفعتين صناعيّتين (17 ثانية وثانية واحدة) مع نفس النقل المضغوط وبصمات القطع. يسجل آخر حالة ورمز خروج العملية وآخر 6000 بايت من سجل المحرك. لا يفحص ملفات المستخدم ولا يطلب OAuth أو مفاتيح. يستخدم مورد Colab الخاص بالمستخدم وقد يستهلك وحدات الحساب. إيقاف العملية المملوكة يجري في finally.

تحقق محليًا من تركيب الدفتر ومن تشغيل مساره كاملًا باستبدال الاستدلال فقط: إنشاء العامل وإعادة استخدامه، تحميل دفعتين وفحص أطوال وبصمات كل المخرجات. هذا لا يعد تجربة CUDA حقيقية. النتيجة الحاسمة التالية هي تقرير الفحص المنفذ في Colab على GPU.
