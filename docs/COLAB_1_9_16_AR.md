# مدار 1.9.16 (51) — إصلاح تهيئة خيار المرحلتين

تقرير 1.9.15 توقف في `STAGE_INSTALL` مع `PY_WORKER_EXIT` قبل تحميل HQ4/HQ3. هذا التقرير المختصر لا يحمل سجل pip ولا يثبت وحده أي أمر فرعي فشل.

وجدت المراجعة اعتمادًا على `venv.EnvBuilder(with_pip=True)` الذي يفشل إذا لم يتوفر `ensurepip` في Python الخاص بـ Debian/Colab. أُعيد إنتاج الفشل على `/usr/bin/python3` من Python 3.12.3 بدون ensurepip. الإصلاح ينشئ البيئة بـ `with_pip=False` ثم يستخدم pip الموجود في Python الأب مع `--python` لتثبيت المكتبات داخل البيئة الخاصة. هذه طريقة pip الرسمية منذ الإصدار 22.3؛ لا يُنزل سكريبت bootstrap ولا تُستبدل مكتبات Python الأب.

- بقيت HQ4 ثم HQ3 والإعدادات والبصمات ومخرجات PCM كما هي.
- بقي مسار Voc_FT السابق والمشغّل والنافذة العائمة وقاعدة 2:30 كما هي.
- كل تثبيت داخل البيئة الإضافية، بما فيه CUDA 12 cuDNN، يستخدم طريقة pip الخارجية نفسها؛ يُعاد تجهيز cache التهيئة القديم مرة واحدة.
- تُورَّث مسارات مكتبات Python الأب صراحةً، لتبقى نسخة Torch/CUDA الموجودة مرئية حتى إذا كانت نواة الدفتر داخل venv أخرى؛ حزم البيئة الخاصة لها الأولوية. كشف اختبار التثبيت الحقيقي هذه الحالة أيضًا، لأن venv المتداخلة ترى مكتبات Python الأساسي افتراضيًا دون مكتبات venv الأب.
- أخطاء التهيئة والتثبيت ومهلته لها رموز محددة: `MUSIC_FX_ENV` و`MUSIC_FX_INSTALL` و`MUSIC_FX_INSTALL_TIMEOUT`. لا يُنسخ نص pip أو الروابط الخاصة إلى تقرير التطبيق.
- يوضح التقرير الآن الخيار الذي بدأ الجلسة: `MUSIC_PROFILE_FX` أو `MUSIC_PROFILE_LEGACY`.

التحقق يشمل إنشاء البيئة دون ensurepip، وتثبيت wheel فعلي محليًا دون شبكة داخل البيئة فقط، واختبار التثبيت الحقيقي للمكتبات ثم HQ4/HQ3 على CPU بنفس دوال تجهيز البيئة المستخدمة في الإنتاج. لا يتوفر GPU هنا، ولا يثبت الاختبار تشغيل T4 أو سرعة حلقة كاملة. إعادة تشغيل المستخدم على Colab هي التحقق النهائي من هذا العطل المحدد.

المصدر الأولي لطريقة التثبيت: [وثائق pip: Managing a different Python interpreter](https://github.com/pypa/pip/blob/main/docs/html/topics/python-option.md).
